# Performance targets

Each target is a release requirement on the reference machines, measured by the
named scenario. A scenario drives the shipped binary or the production entry
point, not a mock, and writes its results as JSON to `bench/results/`.
[status.md](status.md) lists the current measurement against each target.

## Reference machines

| Name | Hardware |
| --- | --- |
| Desktop | Ryzen 9 9950X, RTX 5090, Linux |
| Server | RTX 3080 Ti, Linux |
| Laptop | Integrated GPU (Intel Xe or AMD 780M class), 16 GB, Linux or Windows |

Targets hold on Desktop and Server; Laptop targets are in parentheses where
they differ.

## Media

| Fixture | Contents |
| --- | --- |
| `h264-1080p60` | 60 s, 1920x1080, 60 fps, H.264 High, 20 Mb/s, stereo AAC |
| `hevc-2160p60` | 60 s, 3840x2160, 60 fps, HEVC Main10, 80 Mb/s |
| `prores-2160p30` | 30 s, 3840x2160, 29.97 fps, ProRes 422 HQ |
| `long-gop-scrub` | 10 min, 1080p30 H.264, 10 s GOP |
| `project-10k` | One sequence, 10,000 clips on 50 tracks, 2,000 keyframes, 500 markers |
| `stack-4k` | Three 4K layers, each with Transform, Gaussian Blur, Lumetri basic, and a text clip above |

Fixtures are generated by `cargo run -p aria-bench -- fixtures`, which encodes
the media fixtures with the `ffmpeg` on `PATH`; none is downloaded.

## Targets

| Area | Target | Scenario |
| --- | --- | --- |
| Start | Window interactive in 1 s cold, 500 ms warm | `startup` |
| Project open | `project-10k` open to interactive in 500 ms; save in 200 ms; an autosave holds the UI thread at most 4 ms | `project-io` |
| Play start | Space to the first new frame on screen: 100 ms warm, 300 ms with no decoder open | `play-start` |
| Playback | `h264-1080p60` and `hevc-2160p60` at Full: 0 dropped frames in 60 s (Laptop: `hevc-2160p60` at 1/2) | `playback` |
| Playback, effects | `stack-4k` at 1/2: 0 dropped frames in 30 s (Laptop: 1/4) | `playback` |
| A/V sync | Video presentation within half a frame of the audio clock for every frame | `av-sync` |
| Scrub | Warm scrub (decoder open, frame in cache or one GOP away): next display frame. Cold seek: 150 ms | `scrub` |
| Reverse | `long-gop-scrub` reverse at 1x: 0 dropped frames after the first GOP | `playback` |
| Parameter drag | Dragging an effect value while paused: the Viewer shows the new value within 2 display frames | `param-latency` |
| Timeline | `project-10k`: scroll, zoom, and drag at display refresh, UI frame build at most 4 ms | `timeline-frame` |
| Edit | Any single edit or undo on `project-10k`: 1 ms in the engine, visible on the next display frame | `edit-apply` |
| Export | `h264-1080p60` timeline to H.264 1080p on the hardware encoder: at least 4x real time | `export` |
| Audio | 32 tracks with four shipped effects each at 48 kHz, 256-sample blocks: 0 underruns in 60 s | `audio-load` |
| Memory | Idle with `project-10k` open, frame cache excluded: 500 MB resident | `memory` |
| Plugins | Host call overhead: 1 µs native, 5 µs WASM; a WASM plugin activates in 50 ms; a plugin WGSL effect costs the same as the identical shipped effect within 5 % | `plugin-cost` |

## Running

```
cargo run -p aria-bench --release -- <scenario> [--machine <name>]
cargo run -p aria-bench --release -- all
```

`all` runs every scenario and exits non-zero if any target is missed. Each
result records the machine, GPU, driver, build commit, profile, and the raw
samples, so a regression is compared against the same machine.

Scenarios that need a window run on a private headless compositor. Dropped
frames, A/V offset, and latencies come from the same counters the status bar
and the dropped-frame indicator read.

## Per-frame rules

The preview path is held to these rules; each is checked in the `playback`
scenario by counters, not by inspection:

- No thread is created after playback starts.
- No GPU to CPU readback of a frame that is only displayed.
- No allocation per frame on the render thread after the first second.
- Scopes and meters do not run on the UI thread.
- The UI thread never waits for decode or render.

`ARIA_BENCH_ALLOC_SITES=<n>` prints the call stacks of the first `n`
allocations the render-thread counter records, after the measured window, to
standard error. Capturing a stack slows the frame it lands in; do not read
frame times from a run with it set.
